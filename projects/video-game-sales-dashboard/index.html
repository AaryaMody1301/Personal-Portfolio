02 / The problem

Start with the right question.

The same title may appear on different platforms, and lifetime sales can be mistaken for sales during a particular month or year. Useful comparisons depend on both consistent identities and careful interpretation of the time axis.

03 / My contribution

What I built.

I built the Dash application around data cleaning, interactive callbacks, stable game identities, comparison tools, export workflows, and chronological validation for exploratory forecasts. A deterministic sample-data mode makes the application easier to evaluate.

04 / The approach

Make each step inspectable.

  1. 01

    Define the cohort

    Filter release year, platform, console generation, genre, publisher, critic score, and title.

  2. 02

    Compare consistently

    Explore platform, genre, region, publisher, and release-cohort views. Distinguish same-title releases across platforms using stable identities.

  3. 03

    Take the analysis with you

    Export the currently filtered dataset to CSV or Excel. The supported sample mode is separate from the full dataset.

05 / Evidence

What supports the story.

  • The dataset reports cumulative lifetime sales alongside release dates, not transaction-level monthly or yearly sales.
  • Release-season views describe games released in a period, not the period in which their sales occurred.
  • The repository includes deterministic sample data, regression coverage, and chronological validation for exploratory forecasting.

06 / Scope & limitations

Keep the boundaries visible.

Reported sales coverage and missing values limit the conclusions available from the source. Release timing is not transaction timing, and critic-score associations do not establish causation. Exploratory forecasting should be read within those limits. The diagram is conceptual and is not a capture of the running application.

Good analysis makes the boundaries of the data as visible as the chart.
