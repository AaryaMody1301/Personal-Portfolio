The problem

Job-market analysis needs dependable definitions and repeatable queries before it needs more charts. This project began with a 2023 job-postings dataset from Luke Barousse’s SQL course. I extended that foundation with correctness fixes, portable loading, reusable analytical models, and measured performance work.

The resulting analyses explore salary, demand, hiring trends, and skill relationships. The historical data describes that dataset; it is not a claim about today’s job market.

The approach

  1. Make the data path repeatable. Use portable psql loading and explicit relationships between postings, companies, skills, and job-skill records.
  2. Keep analytical definitions reusable. Build models and correctness contracts instead of copying slightly different filters into each question.
  3. Measure before accepting indexes. Compare plans with EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, FORMAT JSON).
  4. Record the decision. Keep raw evidence and benchmark instructions in the repository, with CI supporting repeatable verification.

The evidence

19.198 → 0.105 ms

Median execution time for the top-paying remote-jobs query, before and after a targeted partial covering index. Shared-buffer activity fell from 4,203 to 38 blocks.

The controlled workload contains 200,000 synthetic job postings, including 40,000 Data Analyst postings and 10,000 remote Data Analyst postings, plus 600,000 job-skill relationships. The acceptance run used PostgreSQL 18.6 on Ubuntu 24.04 and the median of three warm-cache runs per query and state.

Decisions & limits

Accept the targeted indexes

The salary index focuses on salaried remote Data Analyst rows and occupied 736 kB in the benchmark. A second partial covering index occupied 1,944 kB and improved four analytical queries by approximately 7%–27%. Those plans used slightly more shared blocks, so the decision rests on measured execution time and useful coverage.

Reject a speculative skill-pair index

The skill-pair query used neither candidate index and changed by only 0.9%, a difference where runner noise can matter. I retained the existing relationship key rather than adding an index without useful evidence.

The 99.5% reduction applies to one query in one controlled synthetic workload. It is not an overall project speedup or a production latency guarantee. Planner choices depend on data distribution, cache, statistics, hardware, and configuration.

The original course and dataset remain credited in the repository. My contribution is the subsequent correctness, modeling, verification, and performance work.
