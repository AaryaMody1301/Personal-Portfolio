02 / The problem

Start with the right question.

A plausible SQL patch and a green build are not sufficient evidence of a correct repair. The workflow must connect build failures, SQL and YAML, source shape, dependencies, and documented business rules before modifying a project.

03 / My contribution

What I built.

I built the local diagnosis and repair workflow, inspectable deterministic repair skills, sandboxed validation, and the constrained ambiguity fallback. The final handoff is an approval-ready diff and report rather than an unreviewed deployment.

04 / The approach

Make each step inspectable.

  1. 01

    Read the contract

    Collect the incident, business context, local source/model evidence, and the broken-state dbt build.

  2. 02

    Apply a bounded repair

    Use deterministic skills when the contract determines the edit. For the supported ambiguous dependency case, select only an observed candidate or abstain.

  3. 03

    Check, then hand over

    Run dbt and executable contract checks. Return the diff and evidence for human approval, or explicitly escalate.

06 / Scope & limitations

Keep the boundaries visible.

The primary evaluation covers twelve synthetic cases. It does not establish general repair accuracy on arbitrary dbt projects. The separate ambiguity demonstration is not part of that primary score. The portfolio diagram illustrates the documented workflow; it does not run a repair.

A repair is useful only when its reasoning and checks can be inspected.
