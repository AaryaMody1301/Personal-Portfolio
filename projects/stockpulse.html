SEC ingestion with traceable evidence.

The problem

A financial value needs context: which company, which filing, which reporting period, and which unit. Flattening those differences into a single number makes later comparison difficult to audit.

The ingestion path also needs to tolerate reruns and upstream failures. Re-fetching a filing should not create a duplicate; a failed facts endpoint should not silently erase an otherwise usable filing response.

The approach

  1. Resolve company identity. Normalize ticker and CIK before requesting submissions and company facts. Reuse a stored SEC identity when available.
  2. Bound the transport. Serialize SEC requests within a process, apply a minimum request interval, and use a request timeout. Retry eligible failures up to three attempts, honoring Retry-After within a bounded delay.
  3. Normalize without losing provenance. Retain filing accession, form, concept, taxonomy, unit, and reporting dates. Stable fact and metric keys distinguish records by their source and period.
  4. Persist and report the actual outcome. Use createMany with skipDuplicates, record actual inserted counts, and finish each job as success, partial, or failed.

The submissions and facts requests use Promise.allSettled. A usable response can be persisted even when its companion request fails; the error remains in job metadata. When recent submissions are limited, history backfill is capped at two files per ingestion.

Decisions & limits

Partial completion is useful only when it stays visible. Keeping available source data avoids discarding an entire run, but consumers must inspect job status and freshness before treating it as complete.

The request queue is process-local. Multiple workers would need shared rate coordination. Bounded backfill keeps a run small; it also means one ingestion does not promise a complete historical archive.

The metric normalizer chooses from defined concepts and preferred units. That makes mappings inspectable, while requiring care with coverage, restatements, fiscal periods, and cross-company comparisons.

This is a source-reviewed implementation. Production database configuration, provider credentials, deployment probes, and live browser smoke checks remain in the repository’s release checklist. No production reliability or investment-return claim is made by this case study.
